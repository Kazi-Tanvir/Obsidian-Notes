## SECTION 1: IN-DEPTH THEORY & ARCHITECTURE

### 1. The Real-Time Video Topology Evolution

Building low-latency interactive video systems (video conferencing, remote cloud rendering, live broadcasts) requires choosing the right media transport topology.

┌────────────────────────────────────── WebRTC Media Topologies ──────────────────────────────────────┐

│ │

│ Topology A: Peer-to-Peer Mesh (P2P) ⚠️ │

│ • Every participant sends their video to EVERY other participant directly. │

│ • Upstream bandwidth: O(N - 1) connections! │

│ • Fatal Flaw: Mobile clients crash past 4 participants due to upstream bandwidth exhaustion! │

│ │

│ Topology B: Multipoint Control Unit (MCU) 🖥️ │

│ • Central server decodes all incoming video streams, composites them into a single "Brady Bunch" │

│ grid video frame, re-encodes, and sends ONE stream to everyone. │

│ • Downside: Massive server CPU cost, \$500\\text{ms}+\$ transcoding latency, loss of layout control. │

│ │

│ Topology C: Selective Forwarding Unit (SFU) 🚀 │

│ • Every participant publishes ONE upstream video stream to the SFU server. │

│ • The SFU inspects RTP packet headers and routes (forwards) packets to other participants at wire │

│ speed WITHOUT decoding or re-encoding video payloads! │

│ • Delivers sub-50ms glass-to-glass latency with minimal server CPU overhead! ⚡ │

│ │

└─────────────────────────────────────────────────────────────────────────────────────────────────────┘

### 2. Distributed SFU Architecture (LiveKit & Mediasoup)

Modern production SFUs like **LiveKit** (written in Go) or **Mediasoup** (C++ core with Node.js bindings) decouple the network into two distinct planes:

1.  **The Signaling Plane (WebSocket / HTTP)**:

    - Coordinates Room state, participant joined/left events, and the **SDP (Session Description Protocol) Offer/Answer** negotiation.

    - Typically authenticated using cryptographically signed **JWT tokens** generated by a backend Node.js API service.

2.  **The Media Plane (UDP / SRTP)**:

    - High-throughput UDP sockets processing millions of Secure Real-time Transport Protocol (SRTP) packets per second.

    - Employs **SRTP encryption** with AES-GCM, negotiating cryptographic keys via DTLS (Datagram Transport Layer Security).

### 3. WHIP & WHEP: The Modern WebRTC Ingest/Egress Standard

For over a decade, live streaming relied on **RTMP** (Real-Time Messaging Protocol from Macromedia/Adobe Flash, 1996), which suffered from high TCP latency (\$2\\text{s} - 5\\text{s}\$) and no native browser playback support.

The IETF standardized:

- **WHIP (WebRTC-HTTP Ingestion Protocol)**: A standard HTTP POST endpoint where software like OBS Studio, native cameras, or server pipelines send an SDP offer and receive an SDP answer, instantly establishing an ultra-low latency WebRTC ingestion session.

- **WHEP (WebRTC-HTTP Egress Protocol)**: A standard HTTP POST endpoint allowing web browsers to subscribe to a live stream via native WebRTC using standard HTTP handshakes without proprietary WebSocket protocols.

POST /whip/endpoint HTTP/1.1

Host: media.enterprise.com

Content-Type: application/sdp

Authorization: Bearer <INGEST_TOKEN>

v=0

o=- 2890844526 2890842807 IN IP4 192.0.2.1

s=WHIP Stream Ingest

\... [SDP Offer] \...

### 4. Simulcast & Scalable Video Coding (SVC)

If a room contains 10 viewers where 9 have fiber connections and 1 has a degraded 3G cellular connection, what resolution should the broadcaster publish?

- If the broadcaster publishes 1080p, the cellular viewer buffers and disconnects.

- If the broadcaster publishes 360p, the fiber viewers receive terrible quality.

#### The Simulcast Solution:

The publisher encodes **three separate video resolutions simultaneously** using hardware encoding:

1.  **High Layer (f)**: \$1920 \\times 1080\$ @ 3 Mbps

2.  **Medium Layer (h)**: \$1280 \\times 720\$ @ 1.2 Mbps

3.  **Low Layer (q)**: \$640 \\times 360\$ @ 300 kbps

The SFU monitors real-time feedback from every subscriber using **TWCC (Transport-Wide Congestion Control)**:

- If packet loss or round-trip time (RTT) spikes for a subscriber, the SFU dynamically drops the subscriber to the Medium or Low layer **without interrupting the stream**.

## SECTION 2: DOCUMENTATION CHEAT SHEET

### LiveKit Token Generation in Node.js (livekit-server-sdk):

import { AccessToken } from 'livekit-server-sdk';

export function createParticipantToken(roomName: string, participantIdentity: string, isPublisher: boolean): string {

const at = new AccessToken(

process.env.LIVEKIT_API_KEY!,

process.env.LIVEKIT_API_SECRET!,

{

identity: participantIdentity,

ttl: '2h', // Token expires in 2 hours

}

);

// Grant room permissions

at.addGrant({

roomJoin: true,

room: roomName,

canPublish: isPublisher,

canSubscribe: true,

canPublishData: true, // For real-time chat / data channels

});

return at.toJwt();

}

## SECTION 3: WEEKLY SYSTEM DESIGN & CODING PROBLEMS

### Problem 1: Global Interactive Live Broadcasting Platform (Twitch Scale)

Design a planetary ultra-low-latency broadcasting architecture supporting 10,000 streamers and 1,000,000 concurrent viewers with glass-to-glass latency \$<300\\text{ms}\$:

**Architectural Requirements**:

1.  **Edge Ingestion via WHIP**:

    - Streamers push video from OBS using standard WHIP over WebRTC.

    - Anycast Geo-DNS routes broadcasters to the nearest edge ingestion SFU node.

2.  **Cascaded SFU Distribution Mesh**:

    - For viral streams with 100,000 viewers in a single room, a single SFU server will saturate its 10 Gbps network interface.

    - Architect an Origin-Edge SFU cascade where Edge SFUs pull media from Origin SFUs and redistribute to local viewers.

3.  **Simulcast & WebRTC-to-HLS Fallback Pipeline**:

    - If a viewer's browser or corporate firewall blocks UDP WebRTC traffic, transparently downgrade them to a low-latency LL-HLS / CMAF stream generated by an automated transcoder sidecar.

### Problem 2: LiveKit Token & Webhook Lifecycle Controller in TypeScript

Implement a production-ready **Media Room Controller** in TypeScript:

**Requirements**:

1.  **Next.js / Express Token Dispenser**:

    - Endpoint: POST /api/rooms/token.

    - Validates user session, ensures room name is alphanumeric, and issues a typed AccessToken with appropriate publishing permissions.

2.  **LiveKit Webhook Receiver**:

    - Endpoint: POST /api/livekit/webhook.

    - Validates the incoming cryptographic Authorization header using WebhookReceiver from livekit-server-sdk.

    - Listens for events:

      - participant_joined: Records start time and updates Redis active room counter.

      - track_published: Logs video codec and simulcast layer details.

      - participant_left: Calculates total session duration and bills the customer's account.

3.  **Automated Idle Room Teardown**:

    - If a room remains with 0 active participants for \$>5\$ minutes, dispatches an RPC command to LiveKit API (RoomServiceClient.deleteRoom()) to release server memory and ports.
