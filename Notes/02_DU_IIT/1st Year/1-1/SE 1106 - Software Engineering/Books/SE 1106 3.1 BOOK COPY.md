## 3.1 THE MANAGEMENT SPECTRUM[cite: 1]

Effective software project management focuses on the four P's: people, product, process, and project.[cite: 1] The order is not arbitrary.[cite: 1] The manager who forgets that software engineering work is an intensely human endeavor will never have success in project management.[cite: 1] A manager who fails to encourage comprehensive customer communication early in the evolution of a project risks building an elegant solution for the wrong problem.[cite: 1] The manager who pays little attention to the process runs the risk of inserting competent technical methods and tools into a vacuum.[cite: 1] The manager who embarks without a solid project plan jeopardizes the success of the product.[cite: 1]

### 3.1.1 The People[cite: 1]

The cultivation of motivated, highly skilled software people has been discussed since the 1960s (e.g., [COU80], [WIT94], [DEM98]).[cite: 1] In fact, the "people factor" is so important that the Software Engineering Institute has developed a people management capability maturity model (PM-CMM), "to enhance the readiness of software organizations to undertake increasingly complex applications by helping to attract, grow, motivate, deploy, and retain the talent needed to improve their software development capability" [CUR94].[cite: 1]

The people management maturity model defines the following key practice areas for software people: recruiting, selection, performance management, training, compensation, career development, organization and work design, and team/culture development.[cite: 1] Organizations that achieve high levels of maturity in the people management area have a higher likelihood of implementing effective software engineering practices.[cite: 1]

The PM-CMM is a companion to the software capability maturity model (Chapter 2) that guides organizations in the creation of a mature software process.[cite: 1] Issues associated with people management and structure for software projects are considered later in this chapter.[cite: 1]

### 3.1.2 The Product[cite: 1]

Before a project can be planned, product¹ objectives and scope should be established, alternative solutions should be considered, and technical and management constraints should be identified.[cite: 1] Without this information, it is impossible to define reasonable (and accurate) estimates of the cost, an effective assessment of risk, a realistic breakdown of project tasks, or a manageable project schedule that provides a meaningful indication of progress.[cite: 1]

The software developer and customer must meet to define product objectives and scope.[cite: 1] In many cases, this activity begins as part of the system engineering or business process engineering (Chapter 10) and continues as the first step in software requirements analysis (Chapter 11).[cite: 1] Objectives identify the overall goals for the product (from the customer's point of view) without considering how these goals will be achieved.[cite: 1] Scope identifies the primary data, functions and behaviors that characterize the product, and more important, attempts to bound these characteristics in a quantitative manner.[cite: 1]

Once the product objectives and scope are understood, alternative solutions are considered.[cite: 1] Although very little detail is discussed, the alternatives enable managers and practitioners to select a "best" approach, given the constraints imposed by delivery deadlines, budgetary restrictions, personnel availability, technical interfaces, and myriad other factors.[cite: 1]

### 3.1.3 The Process[cite: 1]

A software process (Chapter 2) provides the framework from which a comprehensive plan for software development can be established.[cite: 1] A small number of framework activities are applicable to all software projects, regardless of their size or complexity.[cite: 1] A number of different task sets-tasks, milestones, work products, and quality assurance points-enable the framework activities to be adapted to the characteristics of the software project and the requirements of the project team.[cite: 1] Finally, umbrella activities such as software quality assurance, software configuration management, and measurement-overlay the process model.[cite: 1] Umbrella activities are independent of any one framework activity and occur throughout the process.[cite: 1]

### 3.1.4 The Project[cite: 1]

We conduct planned and controlled software projects for one primary reason-it is the only known way to manage complexity.[cite: 1] And yet, we still struggle.[cite: 1] In 1998, industry data indicated that 26 percent of software projects failed outright and 46 percent experienced cost and schedule overruns [REE99].[cite: 1] Although the success rate for software projects has improved somewhat, our project failure rate remains higher than it should be.2[cite: 1]

In order to avoid project failure, a software project manager and the software engineers who build the product must avoid a set of common warning signs, understand the critical success factors that lead to good project management, and develop a commonsense approach for planning, monitoring and controlling the project.[cite: 1] Each of these issues is discussed in Section 3.5 and in the chapters that follow.[cite: 1]
