## 3.4 THE PROCESS[cite: 1]

> **ADVICE:** Once the process model is chosen, populate it with the minimum set of work tasks and work products that will result in a high-quality product-avoid process overkill![cite: 1]

The generic phases that characterize the software process-definition, development, and support-are applicable to all software.[cite: 1] The problem is to select the process model that is appropriate for the software to be engineered by a project team.[cite: 1] In Chapter 2, a wide array of software engineering paradigms were discussed:[cite: 1]

*   the linear sequential model[cite: 1]
*   the prototyping model[cite: 1]
*   the RAD model[cite: 1]
*   the incremental model[cite: 1]
*   the spiral model[cite: 1]
*   the WINWIN spiral model[cite: 1]
*   the component-based development model[cite: 1]
*   the concurrent development model[cite: 1]
*   the formal methods model[cite: 1]
*   the fourth generation techniques model[cite: 1]

The project manager must decide which process model is most appropriate for (1) the customers who have requested the product and the people who will do the work, (2) the characteristics of the product itself, and (3) the project environment in which the software team works.[cite: 1] When a process model has been selected, the team then defines a preliminary project plan based on the set of common process framework activities.[cite: 1] Once the preliminary plan is established, process decomposition begins.[cite: 1] That is, a complete plan, reflecting the work tasks required to populate the framework activities must be created.[cite: 1] We explore these activities briefly in the sections that follow and present a more detailed view in Chapter 7.[cite: 1]

### 3.4.1 Melding the Product and the Process[cite: 1]

> **ADVICE:** Remember: framework activities are applied on every project-no exceptions.[cite: 1]
> **POINT:** Product and process decomposition occur simultaneously as the project plan evolves.[cite: 1]

Project planning begins with the melding of the product and the process.[cite: 1] Each function to be engineered by the software team must pass through the set of framework activities that have been defined for a software organization.[cite: 1] Assume that the organization has adopted the following set of framework activities (Chapter 2):[cite: 1]

*   **Customer communication**-tasks required to establish effective requirements elicitation between developer and customer.[cite: 1]
*   **Planning**-tasks required to define resources, timelines, and other project-related information.[cite: 1]
*   **Risk analysis**-tasks required to assess both technical and management risks.[cite: 1]
*   **Engineering**-tasks required to build one or more representations of the application.[cite: 1]
*   **Construction and release**-tasks required to construct, test, install, and provide user support (e.g., documentation and training).[cite: 1]
*   **Customer evaluation**-tasks required to obtain customer feedback based on evaluation of the software representations created during the engineering activity and implemented during the construction activity.[cite: 1]

The team members who work on a product function will apply each of the framework activities to it.[cite: 1] In essence, a matrix similar to the one shown in Figure 3.2 is created.[cite: 1] Each major product function (the figure notes functions for the word-processing software discussed earlier) is listed in the left-hand column.[cite: 1] Framework activities are listed in the top row.[cite: 1] Software engineering work tasks (for each framework activity) would be entered in the following row.5[cite: 1] The job of the project manager (and other team members) is to estimate resource requirements for each matrix cell, start and end dates for the tasks associated with each cell, and work products to be produced as a consequence of each task.[cite: 1] These activities are considered in Chapters 5 and 7.[cite: 1]

> 5 It should be noted that work tasks must be adapted to the specific needs of a project.[cite: 1] Framework activities always remain the same, but work tasks will be selected based on a number of adaptation criteria.[cite: 1] This topic is discussed further in Chapter 7 and at the SEPA Web site.[cite: 1]

### 3.4.2 Process Decomposition[cite: 1]

> **ADVICE:** Always apply the CPF, regardless of project size, criticality, or type.[cite: 1] Work tasks may vary, but the CPF does not.[cite: 1]

A software team should have a significant degree of flexibility in choosing the software engineering paradigm that is best for the project and the software engineering tasks that populate the process model once it is chosen.[cite: 1] A relatively small project that is similar to past efforts might be best accomplished using the linear sequential approach.[cite: 1] If very tight time constraints are imposed and the problem can be heavily compartmentalized, the RAD model is probably the right option.[cite: 1] If the deadline is so tight that full functionality cannot reasonably be delivered, an incremental strategy might be best.[cite: 1] Similarly, projects with other characteristics (e.g., uncertain requirements, breakthrough technology, difficult customers, significant reuse potential) will lead to the selection of other process models. 6[cite: 1]

> 6 Recall that project characteristics also have a strong bearing on the structure of the team that is to do the work.[cite: 1] See Section 3.2.3.[cite: 1]

Once the process model has been chosen, the common process framework (CPF) is adapted to it.[cite: 1] In every case, the CPF discussed earlier in this chapter-customer communication, planning, risk analysis, engineering, construction and release, customer evaluation-can be fitted to the paradigm.[cite: 1] It will work for linear models, for iterative and incremental models, for evolutionary models, and even for concurrent or component assembly models.[cite: 1] The CPF is invariant and serves as the basis for all software work performed by a software organization.[cite: 1]

But actual work tasks do vary.[cite: 1] Process decomposition commences when the project manager asks, "How do we accomplish this CPF activity?"[cite: 1] For example, a small, relatively simple project might require the following work tasks for the customer communication activity:[cite: 1]

1.  Develop list of clarification issues.[cite: 1]
2.  Meet with customer to address clarification issues.[cite: 1]
3.  Jointly develop a statement of scope.[cite: 1]
4.  Review the statement of scope with all concerned.[cite: 1]
5.  Modify the statement of scope as required.[cite: 1]

These events might occur over a period of less than 48 hours.[cite: 1] They represent a process decomposition that is appropriate for the small, relatively simple project.[cite: 1]

Now, we consider a more complex project, which has a broader scope and more significant business impact.[cite: 1] Such a project might require the following work tasks for the customer communication activity:[cite: 1]

1.  Review the customer request.[cite: 1]
2.  Plan and schedule a formal, facilitated meeting with the customer.[cite: 1]
3.  Conduct research to specify the proposed solution and existing approaches.[cite: 1]
4.  Prepare a "working document" and an agenda for the formal meeting.[cite: 1]
5.  Conduct the meeting.[cite: 1]
6.  Jointly develop mini-specs that reflect data, function, and behavioral features of the software.[cite: 1]
7.  Review each mini-spec for correctness, consistency, and lack of ambiguity.[cite: 1]
8.  Assemble the mini-specs into a scoping document.[cite: 1]
9.  Review the scoping document with all concerned.[cite: 1]
10. Modify the scoping document as required.[cite: 1]

Both projects perform the framework activity that we call "customer communication," but the first project team performed half as many software engineering work tasks as the second.[cite: 1]
