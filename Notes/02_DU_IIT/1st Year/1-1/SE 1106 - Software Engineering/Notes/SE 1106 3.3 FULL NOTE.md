# 3.3 The Product — Full Note

---

## Overview — The Manager's Dilemma

- At the beginning of a project, **quantitative estimates and an organized plan are required**, but **solid information is unavailable**
- Detailed requirements analysis would provide info for estimates, but takes **weeks or months**
- Requirements may be **fluid** — changing regularly as the project proceeds
- **Solution:** At a minimum, the **scope** of the product must be established and bounded
- If you can't bound a characteristic → list it as a **major project risk**

---

## 3.3.1 Software Scope

- **The first software project management activity** is the determination of software scope

### Scope is Defined by Three Questions

| Question | What it asks |
|----------|-------------|
| **Context** | How does the software fit into a larger system, product, or business context? What constraints are imposed by the context? |
| **Information Objectives** | What customer-visible data objects are produced as **output**? What data objects are required as **input**? |
| **Function and Performance** | What function does the software perform to transform input data into output? Are there any special **performance characteristics** to address? |

### Statement of Scope — Requirements

- Must be **unambiguous** and **understandable** at both management and technical levels
- Must be **bounded** — this means:

| Element | Examples |
|---------|----------|
| **Quantitative data** (stated explicitly) | Number of simultaneous users, size of mailing list, maximum allowable response time |
| **Constraints / Limitations** (noted) | Product cost restricts memory size |
| **Mitigating factors** (described) | Desired algorithms are well understood and available in C++ |

---

## 3.3.2 Problem Decomposition

- Also called **partitioning** or **problem elaboration**
- Sits at the core of **software requirements analysis**
- Uses a **divide and conquer** strategy — complex problem → smaller, more manageable problems

### Two Major Areas of Decomposition

| Area | Description |
|------|-------------|
| **Functionality** | The functionality that must be delivered |
| **Process** | The process that will be used to deliver it |

- During scoping, **no attempt is made to fully decompose** the problem
- Software functions from the statement of scope are **evaluated and refined** to provide more detail before estimation begins
- Both **cost and schedule estimates** are functionally oriented → decomposition is useful

### How Decomposition Works (in practice)

- The statement of scope **evolves** → a first level of partitioning naturally occurs
- Each identified feature = a **subfunction** to be implemented in software
- Each subfunction can be **further refined** if it makes planning easier
