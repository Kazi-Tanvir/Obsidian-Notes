# 3.4 The Process — Full Note

---

## Overview

- The generic phases of the software process: **Definition, Development, and Support** — applicable to all software
- The problem is to **select the appropriate process model** for the software to be engineered
- Avoid **process overkill** — populate the model with the **minimum set of work tasks** that will result in a high-quality product

### Software Engineering Paradigms (from Chapter 2)

| # | Process Model |
|---|---------------|
| 1 | Linear Sequential Model |
| 2 | Prototyping Model |
| 3 | RAD Model |
| 4 | Incremental Model |
| 5 | Spiral Model |
| 6 | WINWIN Spiral Model |
| 7 | Component-Based Development Model |
| 8 | Concurrent Development Model |
| 9 | Formal Methods Model |
| 10 | Fourth Generation Techniques Model |

### Three Factors for Choosing the Process Model

| # | Factor |
|---|--------|
| 1 | The **customers** who requested the product and the **people** who will do the work |
| 2 | The **characteristics of the product** itself |
| 3 | The **project environment** in which the software team works |

- After selection → define a **preliminary project plan** based on the **Common Process Framework (CPF)** activities
- Then → **process decomposition** begins

---

## 3.4.1 Melding the Product and the Process

- Project planning begins with **melding the product and the process**
- **Product and process decomposition occur simultaneously** as the project plan evolves
- Each function to be engineered must pass through the set of **framework activities**

### Common Process Framework (CPF) Activities

| Activity | Tasks Required To... |
|----------|---------------------|
| **Customer Communication** | Establish effective requirements elicitation between developer and customer |
| **Planning** | Define resources, timelines, and other project-related information |
| **Risk Analysis** | Assess both technical and management risks |
| **Engineering** | Build one or more representations of the application |
| **Construction and Release** | Construct, test, install, and provide user support (documentation & training) |
| **Customer Evaluation** | Obtain customer feedback based on evaluation of software representations |

### The Product–Process Matrix

- A matrix is created where:
  - **Rows** = major product functions
  - **Columns** = framework activities
  - **Cells** = software engineering work tasks for each activity
- For each cell, the project manager estimates:
  - **Resource requirements**
  - **Start and end dates** for tasks
  - **Work products** produced as a consequence of each task

> **Key point:** Framework activities **always remain the same**, but **work tasks** are selected and adapted to the specific needs of a project

---

## 3.4.2 Process Decomposition

- The team has **flexibility** in choosing the SE paradigm and the work tasks that populate the model

### Which Process Model for Which Situation?

| Project Characteristic | Recommended Model |
|----------------------|-------------------|
| Small project, similar to past efforts | **Linear Sequential** |
| Very tight time constraints + heavily compartmentalized problem | **RAD** |
| Tight deadline, can't deliver full functionality | **Incremental** |
| Uncertain requirements | Other evolutionary models |
| Breakthrough technology | Other evolutionary models |
| Difficult customers | Other evolutionary models |
| Significant reuse potential | Component-based models |

### CPF is Invariant; Work Tasks Vary

- Once the process model is chosen → the **CPF is adapted to it**
- The CPF works for: linear, iterative, incremental, evolutionary, concurrent, and component assembly models
- The **CPF is invariant** — it serves as the basis for **all** software work
- But **actual work tasks vary** depending on project complexity

### Process Decomposition = "How do we accomplish this CPF activity?"

| Simple Project (Customer Communication) | Complex Project (Customer Communication) |
|---|---|
| 1. Develop list of clarification issues | 1. Review customer request |
| 2. Meet with customer to address issues | 2. Plan & schedule formal facilitated meeting |
| 3. Jointly develop statement of scope | 3. Conduct research on proposed solution |
| 4. Review statement of scope | 4. Prepare working document & agenda |
| 5. Modify statement of scope as required | 5. Conduct the meeting |
| *(~5 tasks, < 48 hours)* | 6. Jointly develop mini-specs (data, function, behavior) |
| | 7. Review each mini-spec for correctness, consistency, no ambiguity |
| | 8. Assemble mini-specs into scoping document |
| | 9. Review scoping document |
| | 10. Modify scoping document as required |
| | *(~10 tasks)* |

- Both perform the **same framework activity** ("customer communication"), but the complex project has **twice** as many work tasks
